# Архитектура

## Точка входа и Windows subsystem

`src/main.rs` — точка входа процесса с Windows GUI subsystem, поэтому при обычном запуске консоль не создаётся. Файл включает диагностику только при наличии `--diagnose`, передаёт закрытый режим помощника `--apply-update` модулю `updater`, а в остальных случаях вызывает `window::run`.

`window::run` включает DPI awareness для каждого монитора, обеспечивает единственный экземпляр через глобальный mutex `CodexUsageMonitor`, регистрирует класс Win32-окна, загружает настройки, создаёт многослойный виджет, по возможности встраивает его в панель задач, регистрирует иконки в трее, запускает фоновые операции и владеет циклом сообщений Win32.

## Состав модулей

| Модуль | Ответственность |
| --- | --- |
| `main.rs` | Режимы процесса и передача управления при запуске |
| `window.rs` | Состояние UI, цикл сообщений, виджет, меню, настройки, таймеры, координация опроса, уведомления, автозапуск и обновления |
| `native_interop.rs` | Перечисление панелей задач, встраивание дочернего Win32-окна, позиционирование, accessibility hooks, сообщения, таймеры и общие помощники |
| `tray_icon.rs` | Динамические индикаторы провайдеров, подсказки, регистрация в shell, balloon-уведомления и ввод из трея |
| `poller.rs` | Координация опроса, poller-ы Claude Code и Antigravity, поиск учётных данных, модель ошибок, форматирование и время сброса |
| `codex_poller.rs` | Поиск Codex CLI и протокол Codex App Server |
| `models.rs` | Независимые от провайдера модели окон использования и агрегированных данных |

| `theme.rs` | Светлая/тёмная тема панели задач из реестра текущего пользователя |
| `diagnose.rs` | Опциональный синхронизированный диагностический файл |
| `updater.rs` | Проверка GitHub Release, помощник портативной замены, определение канала и запуск обновления WinGet |
| `build.rs` | Иконка приложения и строковые/числовые ресурсы версии PE |

## Владение UI и панелью задач

Основной поток владеет созданием окна, меню, отрисовкой, таймерами и обработкой сообщений. `AppState` хранит общий снимок данных провайдеров, текста, повторных попыток, флагов уведомлений, позиции, настроек, языка, темы и состояния обновления. Он защищён глобальным mutex; перед Win32-вызовами, способными синхронно повторно войти в оконную процедуру, блокировка снимается.

Изначально виджет создаётся как layered popup. `native_interop` перечисляет `Shell_TrayWnd` и `Shell_SecondaryTrayWnd`, после чего `window` меняет родителя на выбранную панель задач. При неудаче остаётся запасное окно поверх остальных. Сохранённые `taskbar_index` и `tray_offset` восстанавливают позицию. Перетаскивание ограничивает виджет областью до системного трея и позволяет переносить его между панелями задач.

Отрисовка выполняется GDI в 32-битную поверхность, затем layered window обновляется целиком. Палитры провайдеров, две строки квот, текст, размеры и масштабирование DPI рассчитываются в `window.rs`. `theme.rs` читает `SystemUsesLightTheme`; изменение темы или языка вызывает перерисовку без перезапуска.

Отдельный watchdog каждые две секунды проверяет HWND панели задач. При перезапуске Explorer встроенное дочернее окно уничтожается, поэтому watchdog запускает новый процесс с защитой от цикла перезапусков. Новый процесс ждёт освобождения mutex предыдущего экземпляра.

## Иконки в трее

`tray_icon.rs` создаёт в памяти цветные процентные индикаторы через GDI и регистрирует их с помощью `Shell_NotifyIconW`. Для каждого включённого провайдера существует отдельная иконка. Используется процент короткого окна, а при его отсутствии — недельного. Левый клик меняет видимость виджета, правый открывает общее меню. Предупреждения об авторизации используют balloon-уведомления и отдельный флаг провайдера, чтобы не повторяться в рамках одного эпизода ошибки.

## Координатор опроса и изоляция провайдеров

UI-таймеры запускают `do_poll` в рабочем потоке, поэтому сетевые операции и ожидание процессов не блокируют цикл сообщений. Внутри рабочего потока `poller::poll` последовательно вызывает poller-ы включённых провайдеров. Они логически разделены, но не имеют постоянного отдельного потока каждый.

`PollOutcome` содержит независимые данные и поля `ProviderPollErrors` для Claude Code, Codex и Antigravity. Успешный результат сохраняется даже при сбое другого провайдера. Общая ошибка возвращается только тогда, когда не сработал ни один включённый провайдер. Ошибки авторизации фиксируют уведомление и переключают ожидание на изменение учётных данных; временные сетевые ошибки используют экспоненциальную задержку, ограниченную обычным интервалом опроса.

Таймер обратного отсчёта обновляет только отображаемый текст. После достижения сохранённого времени сброса отдельный быстрый опрос заменяет устаревшие данные квоты.

## Poller-ы провайдеров

### Codex

`codex_poller.rs` ищет `codex.exe`, `codex.cmd`, `codex.ps1` и CLI из активных расширений OpenAI в каталогах VS Code, VS Code Insiders, VS Code OSS, Cursor и Windsurf. Он запускает `codex app-server --disable plugins --disable apps --stdio`, выполняет initialize handshake и запрашивает `account/rateLimits/read`.

Для чтения stdout app-server создаётся короткоживущий поток, передающий JSON-строки через channel. Запросы ограничены 30 секундами, а дочерний процесс при выходе останавливается и присоединяется. Primary и secondary окна нормализуются в короткий и недельный `UsageSection` по длительности.

### Claude Code

Poller Claude в `poller.rs` ищет `%USERPROFILE%\.claude\.credentials.json`, затем `~/.claude/.credentials.json` в перечисленных дистрибутивах WSL. Сначала используется OAuth endpoint использования Anthropic. Если endpoint или время сброса недоступны, выполняется запрос Messages с одним токеном и читаются unified rate-limit headers. При истёкших данных соответствующий Claude CLI в Windows или WSL может быть запущен для самостоятельного обновления токена; все процессы имеют timeout.

### Google Antigravity

Poller Antigravity читает generic credential `gemini:antigravity` через `CredReadW`. Он проверяет production, sandbox и резервные базовые адреса Google Cloud Code, получает проект Code Assist и предпочитает `retrieveUserQuotaSummary`. При отсутствии сводки `fetchAvailableModels` даёт fallback короткого окна. Если групп несколько, предпочитаются квоты Gemini.

## Модель данных и локализация

`UsageSection` хранит доступность, использованный процент, опциональное время сброса и длительность окна. `UsageData` содержит короткое и недельное окно одного провайдера; `AppUsageData` — опциональные данные всех трёх. Отсутствующие и ошибочные данные остаются различимыми в состоянии UI.

`localization/mod.rs` выбирает сохранённый язык либо определяет предпочитаемые языки Windows. Каждый модуль локализации предоставляет одинаковые поля `Strings`. Смена языка обновляет заголовки, меню, подсказки, суффиксы отсчёта, уведомления и названия провайдеров.

## Нативное состояние и настройки

Настройки UI хранятся в `%APPDATA%\CodexUsageMonitor\settings.json`: позиция, интервал опроса, язык, время проверки обновления, видимость виджета и провайдеров. Если после десериализации все провайдеры выключены, Codex включается снова. Автозапуск хранится не в JSON, а в значении `CodexUsageMonitor` ключа `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`; оно считается активным только при совпадении с текущим EXE.

## Диагностика

Диагностика отключена без `--diagnose`. `diagnose.rs` создаёт заново `%TEMP%\codex-usage-monitor.log` и сериализует запись через mutex. В лог попадают состояние операций и классы ошибок, но не значения токенов. Некоторые сообщения содержат пути к исполняемым файлам или credential-файлам и имена WSL, поэтому полный лог нельзя считать автоматически безопасным для публикации.

## Модель потоков

| Контекст выполнения | Работа |
| --- | --- |
| Основной поток Win32 | Сообщения окна, меню, отрисовка, таймеры, решения по настройкам и переходы состояния UI |
| Рабочий поток опроса | Последовательный опрос включённых провайдеров, ожидание credential/process и публикация результата через `PostMessageW` |
| Reader Codex | Чтение stdout одного app-server и передача JSON-строк |
| Worker проверки обновлений | Запрос GitHub Releases и публикация результата |
| Worker/helper портативного обновления | Загрузка в worker; копия helper ждёт завершения, заменяет EXE и перезапускает приложение |
| Watchdog панели задач | Обнаружение замены Explorer/панели задач и перезапуск приложения |

Дополнительные короткоживущие потоки создаются таймерами опроса и действиями обновления; async runtime и постоянного пула потоков провайдеров нет.

## Сетевые границы

- Сеть и авторизация Codex остаются за официальным локальным процессом Codex App Server.
- Claude Code отправляет HTTPS-запросы в endpoint-ы Anthropic usage или Messages.
- Antigravity отправляет HTTPS-запросы в endpoint-ы Google Cloud Code.
- Проверка обновлений обращается к GitHub Releases API; портативный updater загружает asset GitHub Release.
- WinGet делегирует сеть и manifest программе `winget.exe`.

Нативные клиенты `ureq` используют native TLS, timeout 30 секунд и proxy из окружения. Поэтому `HTTP_PROXY`, `HTTPS_PROXY` и `ALL_PROXY` расширяют доверенную границу до указанного proxy.

## Границы credential stores

- Bearer-данные Codex монитор не разбирает. При ожидании входа читаются только метаданные `auth.json`.
- OAuth-файлы Claude разбираются для активного запроса в Windows или через ограниченную по времени команду WSL и не перезаписываются.
- JSON-токен Antigravity читается из Windows Credential Manager и не сохраняется приложением.
- `settings.json` содержит только состояние UI и не должен содержать учётные данные провайдеров.
- Диагностика получает классы ошибок и сообщения об операциях, а не заголовки авторизации.

## Поток обновления

1. Не чаще одного раза в 24 часа или по команде меню `updater` получает последний GitHub Release.
2. Тег сравнивается с compile-time `CARGO_PKG_VERSION` как версия из трёх компонентов.
3. По пути EXE определяется portable или WinGet канал.
4. Portable предпочитает точный asset `codex-usage-monitor.exe`, а при его отсутствии использует первый `.exe` в Release. Затем он проверяет доступность текущего каталога для записи, загружает через файл `.part` и атомарно переименовывает завершённую загрузку в staging. Автоматизация релиза всегда публикует точное предпочтительное имя.
5. Копия работающего EXE становится `updater-helper.exe`. Она ждёт завершения исходного процесса, переименовывает текущий файл в backup, копирует загрузку на его место, восстанавливает backup при ошибке и перезапускает приложение.
6. WinGet запускает PowerShell, который ждёт завершения приложения, выполняет `winget upgrade --id DarhangeR.CodexUsageMonitor --exact` и перезапускает только при успешном exit code.

Опубликованные SHA-256 позволяют выполнить ручную проверку, а CI проверяет их до релиза. Текущий встроенный portable updater не загружает и не проверяет checksum и не проверяет подпись кода; HTTPS и владелец GitHub asset входят в его security boundary.

## Сборка и выпуск

Источник версии — `Cargo.toml`. `build.rs` использует `CARGO_PKG_VERSION`, исходную иконку и `package.metadata.winres` для генерации PE resources. `scripts/package.ps1` и `scripts/verify-release.ps1` проверяют metadata, доступность иконки, отдельный EXE, структуру ZIP, запрещённое содержимое и обе контрольные суммы. GitHub workflow публикуют только прошедшие эти проверки assets.
